# Galaxy → Nexum: authority-aware bookmark reconciliation

## Objective

Render verified WormholeSystems bookmark authority into the **selected** Nexum map's directional signature notes, replacing obsolete B/B.1-derived note writes there while preserving Nexum's independent live cache and every other map's existing behavior.

## Authority and dependencies

- [01-wormholesystems-source-and-sync.md](01-wormholesystems-source-and-sync.md) supplies a validated, map-scoped canonical source snapshot; its freshness for matching must still pass the operator-approved bound below. Do not enable Nexum writes until its unresolved upstream authority and bookmark payload/specification are confirmed.
- `src/nexum-chain.ts` is the pure *legacy* identifier/note planner; `src/nexum.ts` `scheduleChain`/`reconcileChain` and `chainNoteFormat` currently schedule and write legacy notes, defaulting to `{chain}`. `src/tools/nexum.ts` exposes diagnostics and manual reconciliation. `src/nexum-store.ts` persists map-isolated resources/reservations. `docs/nexum.md` establishes that API-key signature-note PATCH exists but API-key `customLabels`/system changes and `bookmarkFormat` changes do not.
- User supplied authoritative record IDs and asked that Galaxy DB/API return the actual records; `~/.eve-sde/galaxy-state.db` is absent and no Galaxy API/resource connection is available here. Exact bookmark syntax, field meanings and supersession versus prior `nexum/chain_note_format` records cannot be inferred; retrieve the specified IDs when access is available and keep authority-dependent rendering/writes disabled until then. The selected-map integration must not fall back to old B/B.1 writes on source failure or missing authority.
- `src/nexum-client.ts:57-63` sends an unconditional PATCH with no version/compare-and-set precondition. A local note check followed by that PATCH is not atomic with a manual Nexum UI edit; no deployed Nexum CAS capability has been verified.
- The permissible maximum age of source observations and Nexum map/signature resources has not been approved. A timestamp that is merely present and non-future is not evidence of sufficient freshness.

## Scope and ordering

1. **Guard legacy writes first.** Introduce a persistent, map-scoped authority mode (`legacy` by default for untouched maps; `wormholesystems` only after explicit targeting). Every path to `scheduleChain`, `reconcileChain`, manual `nexum_reconcile_chain_notes`, and any deferred/in-flight legacy writes must honor the mode under the shared per-map serialization boundary described below. Switching modes cancels/quiesces queued legacy reconciliation for that map and waits for an in-flight PATCH to complete before declaring the switch effective; a write already issued cannot be retroactively canceled. Existing legacy reservation data/diagnostics may remain visible as historical, but cannot become the authority for notes in the target map. Changes to the old `chain_note_format` record must not re-enable legacy writes there. Never globally disable other maps.
2. Build a **pure matching/planning module** consuming one eligible source snapshot, one coherent Nexum cached map state plus signatures/resource timestamps, an explicit operator-approved maximum-age/freshness policy, and the confirmed bookmark rule. Output deterministic proposed changes and categorized skip/conflict diagnostics; no HTTP or DB mutations in this module. Build the bookmark renderer separately from upstream normalization and matching. Verify required tokens, escaping/length limits and exact expected outputs against authority-approved fixtures **once obtained**; until then use explicitly synthetic local fixtures solely to test mechanics, not to certify bookmark semantics. Unknown or unsupported formats make the entire source plan non-writable rather than generating `{chain}` or invented text.
3. Reconcile using the existing Nexum signature-note PATCH endpoint and healthy authorized map-access writer selection. Only changed notes that passed exact matching and ownership checks may be PATCHed; never PATCH Nexum system labels, connections, signatures' identity, or map metadata. Preserve existing optimistic cache update after success and idempotence on echoed `sig.changed` events. Expose a local-only dry-run preview and an explicit target-map apply tool (or on-demand sync apply flag, default false); responses list matched/proposed/skipped/conflicting counts and sanitized per-item reasons. Follow existing Galaxy MCP operator-path conventions behind the user-confirmed Cloudflare Access boundary; do not add an application-auth scheme or claim the deployment Access configuration was verified here. Apply must remain disabled until the activation gate below; no automatic application from incidental Nexum events.
4. Persist note-write provenance per canonical map + Nexum system ID + signature row ID: source identity/revision/digest, source connection and direction, Nexum connection ID and endpoints, rendered note hash/value (safe text only), prior note hash/value if needed for review, successful PATCH timestamp, and last observed Nexum resource freshness. Keep secrets out. An additive migration must not alter existing reservation assignments or ledger history. Record failures separately from successes. Recheck source revision, mode, map identity, Nexum signature/content and connection state in the serialized final check/write stage. If any recheck fails, skip and require a fresh preview/reconciliation. This protects against Galaxy-internal races only; it does not establish atomic ownership against independent Nexum UI/API writers.

## Per-map serialization and write safety

Use one per-canonical-map decision/write boundary, shared by source snapshot replacement/eligibility changes (including fetch failure), mode/target/initial-replacement authorization changes, legacy/manual/deferred reconciliation, source apply, and the corresponding cache/event mutations or invalidations that change note/connection matching. A network fetch may run outside the boundary, but staging a validated snapshot and deciding its eligibility must enter it. Recompute or validate the plan against the current mode, snapshot revision, Nexum resources and ownership **inside** that boundary, hold exclusive map write ownership through each PATCH response and the resulting cache/provenance update, and invalidate stale queued plans rather than allowing them to resume after a mode/snapshot change. A per-process mutex is sufficient only for the documented single-process deployment; multiple writers/processes require an enforceable shared lease/fencing protocol before activation. Do not hold a database transaction open across network I/O. Mode transitions must wait for active writes before completion; do not claim a mode switch can revoke an already transmitted PATCH.

Before any live apply, inspect the actual target Nexum server/API contract to establish whether the signature-note PATCH supports an enforceable version/ETag/`If-Match` (or equivalent atomic conditional update) and verify its behavior against a test instance. If available, require a fresh authoritative note/version read and a conditional PATCH, treating precondition failure as conflict without overwriting, then update cache/provenance only on acknowledged success. The currently implemented unconditional `HttpNexumTransport.patch` is **not** a CAS. If the deployed API has no such support, even a fresh GET, event-stream check and per-map lock leave a residual time-of-check/time-of-use race with manual Nexum edits; do not claim manual notes are fully protected. In that case keep live apply disabled until an explicit operator/product decision accepts this documented residual overwrite risk and specifies permitted scope/operational safeguards, or the Nexum API gains CAS. Fixture/mock tests alone do not establish Nexum CAS support or authorize production writes.

## Interfaces and matching invariants

Use the **canonical map ID**, never map name, to bind configuration, source snapshot, diagnostics, provenance and apply. A match requires: same EVE solar-system ID on each resolved endpoint (not names/classes), the full scanner-side directional signature identity (including code and relevant stable row ID where available), exact source↔Nexum connection identity established from both endpoints and directional signature references, current compatible connection state (not broken/expired), and freshness of **both** source observation and Nexum map/signature cache. Do not match via `whLeadsTo` name, class, partial signature code, stale provisional reservation, or arbitrary first candidate. If the upstream cannot establish identity for a still-unmapped connection, leave it unmatched; never mutate topology to manufacture a match. Require one-to-one correspondence in both directions where data exists; multiple candidates, reused codes, mismatched reverse references, unknown connection state, conflicting endpoint IDs, missing timestamps and stale snapshots are explicit skips. A safely known single direction can be planned only if confirmed upstream authority permits directional-only entries; otherwise skip it. Preserve Nexum map isolation even when two maps contain the same EVE systems/signatures.

Freshness is a **fail-closed activation prerequisite**: require an explicit, persisted, operator-approved maximum-age/freshness bound for the selected map covering both source observations and Nexum map/signature resources (separate bounds are acceptable if explicitly approved). Do not supply an arbitrary numeric default or treat a present, non-future `fetched_at` as fresh. Apply the bound against the decision time to validated source observation/retrieval evidence and each required Nexum map/signature resource timestamp; missing, future, stale, or unverified observation evidence is ineligible. Re-evaluate all required ages at preview and again in the serialized final apply check, since a previously fresh plan can expire. Until the policy is configured, source snapshot retrieval and local status remain available, but diagnostics must label freshness **unconfigured/unknown**, potential identity correlations **unverified/ineligible** (not fresh or complete matches), proposed writable changes zero, and reconciliation must perform zero PATCHes. A configured bound does not waive source authority, ownership, mode, or the conditional-PATCH/no-CAS activation gate.

Synthetic previews carry their `canonicalMapId`; `NexumStore` checks it against both the requested target map and the stored fixture's map identity when saving and reading, independently of revision equality. The synthetic planner also checks duplicate source signature keys and contradictory Nexum-system-ID ↔ EVE-system-ID mappings at runtime; any ambiguity skips the source connections before a match is produced, even if a caller bypasses fixture validation.

Bookmarked note output is derived **only** from confirmed WormholeSystems authority and verified directional data; do not splice a legacy `{chain}` result into it. If upstream bookmark data conflicts with newer verified authority or has unresolved supersession, suppress writes and surface a blocker. Present the exact planned string and its source revision in preview so an operator can check it before apply. The UI's **Signature bookmark** format must be `{notes}` to copy note text verbatim; Galaxy cannot set that UI preference over Nexum's key API. Report it as a deployment prerequisite, not a silently applied setting.

Ownership: preserve manual and unrelated Nexum notes wherever ownership can be established; do not assert protection from edits racing an unconditional PATCH. An initial replacement of pre-existing B/B.1 notes requires explicit operator confirmation of target map and approved replacement scope based on preview; prove which notes are legacy-managed via existing plan/current note comparison or recorded provenance. If ownership cannot be proven, skip and report manual review. On later syncs only update a row if its current note still equals the last successfully written managed note (or is an explicitly authorized initial legacy replacement); under a verified CAS use its atomic precondition to preserve edits arriving between read and PATCH. Never clear notes simply because a WormholeSystems record disappears, becomes stale or a link breaks. A successful unchanged application makes zero PATCHes.

Failures: read/snapshot/validation/stale/conflict conditions cause **no** writes, retain old Nexum notes and last good source snapshot with visible stale/ineligible status. Per-note Nexum 401/403 marks writer unavailable for writes without stopping map reads/events; 429/transient failures respect retry limits and `Retry-After`, retain uncommitted notes for a future explicit attempt, and never mark failed writes as completed. Partial success is reported per item and safe to retry because provenance and cached notes reflect only successful PATCHes. Preview has zero upstream calls. No source records, inference, or cached stale values may be represented as confirmed fresh Nexum state.
