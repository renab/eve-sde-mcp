# Source signature names and reconciliation outcomes (Galaxy ↔ Nexum)

## Objective and authority

Synchronize WHS-derived signature display names into the existing Nexum signature `name` field **only for source-owned rows**, and make partial reconciliation and skipped cleanup legible without weakening guards. WormholeSystems (WHS) is canonical for topology and naming: its signature view has a scan code, category, type and connection, but no separate site/name field. Render wormholes as `<scan code> - <wormhole type>` (for example `CLA-864 - O477`); render every other signature as the exact token `Unknown`. Nexum is the bookmark/note export surface, not the authority for signature names. There are **no user-authored annotations to preserve on Galaxy-owned nodes**: Galaxy-derived WHS notes and source fields on its owned rows must follow WHS. Protect unrelated, unmatched, or unknown-ownership rows and retain exact link/note matching safeguards.

Authority: [04-wormholesystems-topology-and-signatures-apply.md](04-wormholesystems-topology-and-signatures-apply.md), especially complete projection F-1, ownership, checkpoint, freshness, deletion and retry rules; [02-wormholesystems-nexum-reconciliation.md](02-wormholesystems-nexum-reconciliation.md) for the separate, explicitly invoked linked-note PATCH and matching gate (its assumption that observed nonempty notes are manual is superseded **for proven Galaxy-owned rows only** by this newer user decision); Galaxy `src/wormholesystems-adapter.ts:235-276`, `src/wormholesystems-fixture.ts`, `src/wormholesystems-reconciliation.ts:258-306`; Nexum `server/src/services/wormholesystemsTopology.ts`, `server/src/routes/apiV1.ts`, `server/src/migrate.ts`, `web/src/components/ui/SignaturePane.tsx`. Nexum's v2 closed signature input allows `sourceSignatureId`, `sourceSystemId`, `sourceConnectionId`, `sigId`, `sigType`, `whType`, not `name`. Current inserts/updates and managed baselines omit `name`; nonempty name currently prevents deletion. UI displays/edits `name`. The Galaxy v3 source adapter captures validated `signatureCode`, `signatureCategoryName` and related `wormholeName` (and `signatureTypeId`, which is **not** a name lookup key). The existing Nexum v3 request and Galaxy request validator already carry `name`; this change requires no Nexum v4 wire version.

## Dependency-ordered implementation slices

1. **Nexum protocol and compatibility first.** Use the strict `schemaVersion:3` **Nexum topology request** (distinct from existing Galaxy source-envelope v3), retaining v1/v2 parsing/replay for legacy checkpoints until this map/source accepts v3. Each v3 signature requires `name: string | null`: retain null only as the already-specified compatibility no-change sentinel (not emitted by fresh Galaxy projection); Galaxy emits explicit non-null rendered strings including `Unknown`. Names must be exact, 1–256 characters, nonempty after whitespace validation, without leading/trailing whitespace or control characters (including Unicode controls); no truncation, case folding or HTML markup conversion. Reject missing/extra/malformed keys before mutation. Normalize/hash name with all managed desired fields. Once v3 accepted, reject v1/v2 writes for that map/source with 409. v2 → v3 at identical `fetchedAt` conflicts; require a genuinely newer validated fetch. Preserve idempotent exact replay, stored partial outcome and existing auth/map lock. No new `map_signatures` column; any outcome persistence change must be additive and retain existing ownership/checkpoints.
2. **Galaxy name projection (Principal Reviewer F-1, high, owner=architect).** For every validated full-detail source signature use the exact validated `signatureCategoryName`, `signatureCode` and consistent validated `wormholeName` relationship. Only exact category `Wormhole` with an assigned nonempty scan code and validated related nonempty wormhole name renders `signatureCode + " - " + wormholeName` (e.g. `CLA-864 - O477`, `MOF-032 - B274`); non-wormholes and unsupported/absent categories render exactly `Unknown`. For a `Wormhole`, `Unknown` is permitted only when source evidence explicitly records an unassigned/null scan code or when the otherwise structurally coherent wormhole relationship has an absent/empty name (including no wormhole record/name without a partial or contradictory reference). An uncaptured `signatureCode` field is not an evidenced unassigned code: it is a source-identity failure blocking the **entire projection with zero PUTs**. A partial, malformed or contradictory wormhole relation (including a name without a consistent relation) likewise blocks the **entire projection with zero PUTs**; `Unknown` must never conceal missing assignment evidence or invalid relations. Valid fallback cases receive bounded keyed diagnostics without omitting any source-present signature. Do not resolve `signature_type_id` against EVE SDE `invTypes.typeID`, use `signature_type.name`, Nexum’s existing name, a generic type-name fallback or a category label as a display name. Validate rendered names against the existing v3 1–256-character and control/whitespace constraints; invalid evidence fails closed, never truncates or substitutes another source. Freeze rendered names and source-field provenance with the current fresh v3 source fetch before PUT; same-fetch retry reuses the exact frozen v3 payload and digest, never recomputes from changed data. Galaxy source envelope remains v3; old snapshots stay read-only and are not upgraded by inference. Local preview reports bounded keyed render/fallback status with no upstream calls/writes.
3. **Nexum safe owned-row reconciliation.** New source-created signatures persist the explicit derived name (`Unknown` included); only legacy/other v3 callers using `name:null` retain the existing empty default. Before updating an owned row, compare managed fields to its baseline. For legacy ownership without a name baseline, bootstrap its actual name when ownership and managed row identity are verified, whether empty or nonempty; an unbaselined nonempty Nexum name is not source authority. Where the map/source ownership record proves Galaxy created this exact row and the row still matches its managed identity/fields, a current WHS-rendered non-null name replaces the stale display name; do not infer provenance for a preserved/manual or ambiguous row. After bootstrap, replace the old/stale source-derived display name with the newly rendered non-null name regardless of whether the current display name still equals its baseline; a Nexum display value is not competing evidence against the current WHS-rendered name; `name:null` preserves actual name and baseline. Record the actual persisted name in the new managed baseline only after a successful write; name drift alone is not a competing authority or a blocker. If ownership/identity is missing, ambiguous, or contradicted, preserve and emit a name-specific conflict without stamping a desired baseline. An exact-code manual row remains preserved, never renamed/claimed even if its name differs. Maintain other managed-field identity checks, unknown-row protection, connection refs and creation/deletion order. On a verified Galaxy-owned row, neither stale `name` nor Galaxy-derived `notes` is treated as an independent manual edit; other unrecognized fields and dependent/manual connections still require their existing safety checks. A signature absent in a later eligible complete snapshot may be deleted only with source/map ownership proof, complete fresh source evidence and the existing dependency/unknown-content safeguards; a drifted name or WHS-derived note alone must not indefinitely pin the owned row. Do not retroactively delete protected rows to reduce counts.
4. **Nexum + Galaxy actionable outcomes.** Extend existing bounded checkpointed response, not a mutating cleanup endpoint. Retain counts and mappings; report each blocked desired item, preserved incompatible manual counterpart and skipped absent-row deletion with `itemKind` (`system|signature|connection`), stable source item ID, stable reason code and affected managed field(s) where applicable. Include per-kind/outcome totals and omitted counts so truncation is not mistaken for no conflicts; provide bounded keyed safely deleted source IDs (or equivalent per-row delete results) as well as deletion counts. Distinguish `name_unknown` (Galaxy: valid fallback for non-wormhole/unsupported category, explicitly unassigned code or absent/empty wormhole name on a coherent relation, with `Unknown` explicitly sent), `name_ownership_unknown`, `name_identity_conflict`, `manual_name_not_managed`, and precise existing dependency/manual/managed-change/identity reasons; no blanket generic ID list. Never classify uncaptured source code or incomplete/contradictory wormhole relation as `name_unknown`: these are whole-projection blockers, not per-row fallback or target partial outcomes. Persist committed partial outcomes for exact replay or reconstruct safely under the same map lock. Galaxy displays acknowledged per-kind counts, partial/checkpoint state and keyed deletion/skip outcomes; transport timeout remains indeterminate, never success. No credentials, raw source payloads, notes or arbitrary DB content in diagnostics.

### F-1 (high, architect): durable frozen Galaxy request and retry

Before the first Nexum PUT, durably persist a bounded, validated **exact name-enriched Nexum v3 request** (including a non-null WHS-derived `name` per source signature, `Unknown` where required), its normalized request digest, and provenance tying it to the validated Galaxy v3 source snapshot/revision, `fetchedAt`, source identity, selected canonical/Nexum map binding, configuration/policy revision and WHS name-rendering evidence. Persist the complete request in Galaxy's per-map source-run/write-attempt state, atomically with its frozen-request metadata; enforce the existing request/body cap and local storage limits and fail closed without sending if persistence fails. Do not store credentials or unbounded raw source bodies. The persisted request is the retry authority, not the original fixture or a new projection. Record attempt/indeterminate/acknowledged state durably so a process restart can identify the in-flight attempt without substituting the latest source run or a later map's payload; serialize with the map-decision boundary. On retry after an indeterminate response, load and integrity-check the same stored bytes/normalized digest and provenance; send that **identical request unchanged** only while the original source remains eligible under 04's current policy, 60-second freshness, map/source/config/credential authorization and version gates (also observe Nexum's ceiling). A missing/corrupt/mismatched frozen request blocks retry: never regenerate it by calling `validateWormholeSystemsFixture` + `reconcileFreshTopologyLocked`, re-render names against changed WHS evidence, restamp `fetchedAt`, or reinterpret an old source envelope. Once stale or invalidated, require a genuinely new complete source fetch and reconcile the previous indeterminate result via checkpoint/authorized GET evidence rather than claim success. Current `src/wormholesystems.ts:862-894` retries by reprojecting the fixture and must be changed in implementation.

### F-2 (high, architect): additive Nexum checkpoint migration

Nexum `server/src/migrate.ts` currently creates `wormholesystems_topology_checkpoints.schema_version` with `CHECK (schema_version IN (1,2))` (around line 1069). Before accepting request v3, add an idempotent additive migration which replaces that constraint on **existing** databases as well as fresh installs with `IN (1,2,3)`; retain the default, existing `(map_id,source_identity)` keys, fetched times, digests, `result_json`, all ownership rows and prior accepted results. Do not rewrite historical schema versions, checkpoints or ownership to 3. Schema validation must recognize only these versions, and v3 acceptance advances this map/source's schema version in the same locked transaction as its committed result. An accepted-v3 map/source rejects downgrade v1/v2 (including otherwise-valid newer timestamps); existing v1/v2 exact replay retains its original result until a genuinely newer validated v3 request is accepted. Verify migration order before enabling the route: updating parser/response alone cannot bypass the old PostgreSQL CHECK.

### F-3 (medium, architect): actionable mixed partial results

Define bounded, deterministic structured results for each blocked **desired** system/signature/connection, each preserved incompatible manual counterpart, each skipped unsafe absent-owned deletion and each safely deleted owned row. Every per-item outcome identifies `itemKind`, stable `sourceItemId` (not just scanner code or Nexum UUID), a stable reason code, and affected managed field name(s) when applicable; keyed delete results carry the deleted source item ID and kind. Keep response compatibility with the existing counts/mappings; report totals **by kind and outcome class** independently of capped item arrays, plus explicit omitted counts for each truncated class. Classification must distinguish blocked creation/update, preserved manual match, skipped deletion and successful deletion; name-unknown fallback diagnostics must not imply a failed whole snapshot. Canonically order/bound results so replay of a committed partial returns the same totals, item details, truncation and omission counts, not new all-zero counters or a changed classification. Persist the full committed bounded outcome at the checkpoint (or deterministically reconstruct from committed evidence under the same map lock) without exposing raw notes, credentials or arbitrary database content. Galaxy must surface these distinctions and never equate acknowledged partial, zero sampled conflicts or a timeout with full success.

## Galaxy-managed WHS notes (explicit amendment to unit 02 for owned rows)

The note writer remains a **separate explicit operation**, never part of the topology PUT or an unconnected signature. Retain unit 02’s fresh exact source-edge/direction match, validated aliases/status, healthy target observation, same-map serialization, and existing unconditional signature PATCH/no-CAS race disclosure. For a target signature whose exact map, source identity, source signature ID and Nexum row ID are **proven source-owned**, replace its prior WHS-derived `notes` with the newly rendered WHS note even when Nexum currently contains a different nonempty string; do not use that value as authoritative or classify it as a user-authored override. If WHS lacks valid directional evidence, do not fabricate a note, destination, or clearing instruction. For preserved/manual or uncertain rows retain unit 02’s empty-or-equal observed-note gate and report skipped notes rather than adopting or overwriting them. The topology PUT must not populate `notes`, shortcut note matching, or silently make separately ineligible rows note-eligible.

Because ordinary Nexum signature GET does not attest ownership, implementation must obtain trusted proof of the exact mapping from the authenticated map/source ownership boundary (or an equivalently verified committed ownership mapping, revalidated against fresh target identity). A past Galaxy tool response, scan-code match, map EVE ID, or caller assertion alone is insufficient. Provide a bounded, map-bound read-only ownership attestation on Nexum for the selected source identity and row IDs (or an equivalently server-verified authorization/ownership check in the existing PATCH path), and recheck target identity before applying a note. Do not expose arbitrary ownership records, permit a generic write key to impersonate the integration, or require direct Galaxy DB access. This map-bound, fresh ownership proof is the specific authority that supersedes unit 04’s no-authority-record blocker caveat for the separately invoked owned-row note PATCH only; it does not loosen the gate for manual/unknown rows or turn the topology PUT into a note writer. A successful note PATCH on a verified owned row still has the existing 02 external-edit race; do not claim transactional CAS or preserve the previous Nexum text as an independent note. When deleting safely absent owned rows, source-derived note content must not alone block cleanup, but an ambiguous ownership/row identity or independently maintained dependent remains protected. Report separately note-applied, note-skipped-for-matching, and note-skipped-for-unproven-ownership outcomes.

## Invariants and boundaries

- Galaxy source-envelope v3 and Nexum request v3 are **separate protocols**. Roll out Nexum acceptance before Galaxy emits v3; keep accepted-v3 downgrade guard and legacy checkpoint replay. Respect 04's map-bound authorization, Galaxy 60-second freshness gate, server ceiling, map lock, atomic transaction, same-timestamp digest conflict, same-operation write, failure/retry policy and note separation.
- `name` is the WHS-derived display label: exact validated wormhole scan code + ` - ` + validated related wormhole name, or explicit `Unknown`; it is distinct from `sigType`, `whType`, `sigId`, connection fields, notes and linked bookmarks. Neither WHS `signature_type_id` nor an EVE SDE name supplies it. On a proven owned row, the current non-null derived name (including `Unknown`) supersedes even a stale SDE-derived, drifted or unbaselined Nexum display name; notes derived from WHS are not Nexum-owned annotations. Do not overwrite unrelated/unknown-ownership rows or manual exact-code matches.
- Only absent, unchanged, source-created rows with safe dependencies can be deleted on a fresh complete fully projected snapshot; for a WHS-absent Galaxy-owned system, `position_x/position_y`-only Nexum layout drift does not count as a change and does not block otherwise safe deletion. Other managed-field changes, uncertain ownership, unrelated/manual rows and dependent/manual content retain their protections. A committed partial reconciliation does not imply every item synchronized. Projection failure sends zero PUTs and authorizes zero deletion; target conflicts permit independent safe writes but are never treated as deletion instructions. No direct Galaxy access to Nexum DB.
- Current observed accepted partial outcome: systems 1 created/1 updated/0 deleted/1 preserved; connections 1 created/0 deleted; signatures 2 created/91 deleted; 12 generic conflict IDs `[110,121,122,123,124,723,642,113,124,125,126,127]`. Do **not** assign item kind/cause, infer unsafe deletions, or weaken guards from these IDs; separate read-only investigation determines exact reasons.
